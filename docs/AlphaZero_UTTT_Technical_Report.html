1執行摘要雙側

終極井字棋（Ultimate Tic-Tac-Toe, UTTT）是經典井字棋的遞移化擴展：棋盤由 3×3 個小九宮格組成，共 81 個落子格；玩家落子後，下一步被強制限制在該格對應的小九宮格，僅當該小九宮格已填滿或已分勝負時，才獲得「全盤自由落子權（Wildcard）」。這個遞移規則把「區域戰術」與「全域戰略」綁在一起，使得局面樹遠比 81 格的表面大小更為深廣：任何一手的價值都同時取決於它對所屬小九宮格的影響，以及它把對手導向哪一個小九宮格。傳統的窮舉式搜尋在這種棋上迅速失守——普通 3×3 井字棋只有 \(3^9 = 19683\) 種盤面，而 UTTT 的搜尋樹在實用時間內無法靠固定深度 Minimax 覆蓋。

本報告針對「以 AlphaZero 從零自對弈學會 UTTT」的專案，沿遊戲側（Game Side）與深度學習側（Deep Learning Side）雙線展開，並以 game.py、ai.py、alphazero.py 三個模組的真實程式碼為唯一事實來源。

  • 遊戲側成果：實作並優化了完整的傳統演算法家族——Basic 規則引擎、Minimax（alpha-beta）、Minimax Pro（negamax + 置換表 + Killer Move + LMR + Aspiration Window + 疊代加深）、MCTS（UCT）、MCTS+RAVE、MCTS+GRAVE、Flat MCTS、Solver（39 殘局表）與開局書；並完成位板（bitboard）表示、啟發式 rollout、樹重用、物件池、D4 對稱去重與多執行緒並行等工程優化（決策 D12）。現行優化下 MCTS/RAVE/GRAVE 於 30 局/對、300 sims 循環賽中統計持平（51.7% / 48.3% / 45.0%，D21 取代 D8/D12 的舊排名）。
  • 深度學習側成果：雙頭殘差網路（4 通道輸入、128 通道 × 5 殘差塊、Policy 81 維 / Value 1 維）經 6000 局自對弈訓練後，總損失由 2.46 降至 0.094；200 sims 對隨機對手 40 盤取得 38 勝 1 平 1 負（95%）。對普通 MCTS 在同預算（800/800）下得分率僅 23.3%（6W/2D/22L，30 盤）——這個結構性差距點出了「全展開＋先驗引導搜尋」與「啟發式 rollout 深戰術搜尋」的本質差異，也是本報告第 6 章分析的重點。
  • 兩側協作：遊戲側的啟發式 rollout（ai._rollout_move）與位板搜尋（BitUltimateGame）被 AlphaZero 的葉節點評估與 MCTS 搜尋直接復用；位板表示同時服務傳統引擎與神經搜尋，形成單向依賴 game.py → ai.py → alphazero.py 的乾淨架構（D2）。

2.2 active_macro 與 Wildcard：legal_moves() 的兩種分支

UltimateGame.legal_moves()（第 85–96 行）是規則的心臟，直接對應 UTTT 的兩條分支：

  • 受限分支：當 active_macro is not None 且該宏觀格仍開放（macro_open），唯一合法集合是 [(active_macro, i) for i in range(9) if 空格]——玩家被鎖死在對手上一步所指的小九宮格。
  • 自由分支（Wildcard）：否則枚舉所有仍開放的宏觀格 m，並列出其所有空格。此分支會在兩種情況觸發：active_macro 為 None（如開局或上一手指向已結束的格子），或是 active_macro 已不再開放。

make_move()（第 101–111 行）的更新順序是規則一致性的關鍵：(1) 驗證佔位並落子；(2) 若小九宮格分出勝負則寫入 macro[macro] = w，否則若填滿則寫入 'D'（平局的小九宮格是中性、不再開放）；(3) 以 macro_open(micro) 判斷下一步的 active_macro，若不可開放則為 None（即 Wildcard）；(4) 最後才換手。macro_open()（第 82–83 行）同時檢查宏觀格未被佔領且內部仍有空格，確保「已定局或已滿」的格子永遠不會被誤用。

2.3 勝負判定與平局

winner()（第 113–117 行）只在宏觀層判定：檢查 LINES 八條連線（三行、三列、兩對角線）上是否出現三個相同的 X/O 宏觀佔領。小九宮格內部勝負由 micro_winner() 委託共用的 line_winner()（第 17–24 行）。is_full() 定義為「所有宏觀格皆不可開放」，而 result() 依序回傳：宏觀勝者 → 全滿平局 'D' → None（未結束）。值得注意的是 UTTT 的平局比普通井字棋常見得多：小九宮格可以互為平手（'D'），只要宏觀層無人連線，即使棋盤近乎全滿仍可能和棋。

2.4 BitUltimateGame：位板表示與等價性

位板版把 81 個格子的 X/O 佔位壓成兩個 81-bit 整數，宏觀佔領壓成兩個 9-bit 整數，並以 __slots__（第 150 行）省去執行個體字典的記憶體。其關鍵設計：

  • 小九宮格取掩碼：_micro_bits(m) = ((x | o) >> (m * 9)) & 0x1FF（第 185–186 行），一次位移即可取得某宏觀格的 9-bit 佔位。
  • 連線判定：_win_mask()（第 188–194 行）以 mask & line == line 檢查八條 3-bit 連線掩碼，X/O 各查一次。
  • 開放性：macro_open()（第 204–207 行）先查宏觀掩碼是否已定局，再比較 _micro_bits(m) != 0x1FF——一個 != 即完成「是否填滿」的檢查。
  • 落子：make_move()（第 224–238 行）以 bit = 1 << (m * 9 + i) 定位，重複落子因 (self.x | self.o) & bit 為真而拋出 ValueError，與列表版語意一致。
  • 平局顯示：macro property（第 275–280 行）在掩碼未定局但九格全滿時回傳 'D'，讓 UI 呈現與列表版完全一致。

class BitUltimateGame:
    """Ultimate board stored as bit masks (X/O 81-bit, macro 9-bit).

    Same interface as UltimateGame (legal_moves / make_move / result /
    clone / current / active_macro / micro / macro) so the MCTS family can
    search on the bit representation and hand moves back to the list UI.
    """

    __slots__ = ('x', 'o', 'mx', 'mo', 'current', 'active_macro')

    def __init__(self):
        self.x = 0
        self.o = 0
        self.mx = 0
        self.mo = 0
        self.current = X
        self.active_macro = None

    @classmethod
    def from_game(cls, game):
        g = cls()
        for m in range(9):
            for i in range(9):
                c = game.micro[m][i]
                if c == X:
                    g.x |= 1 << (m * 9 + i)
                elif c == O:
                    g.o |= 1 << (m * 9 + i)
            if game.macro[m] == X:
                g.mx |= 1 << m
            elif game.macro[m] == O:
                g.mo |= 1 << m
        g.current = game.current
        g.active_macro = game.active_macro
        return g

    def clone(self):
        g = BitUltimateGame()
        g.x, g.o, g.mx, g.mo = self.x, self.o, self.mx, self.mo
        g.current = self.current
        g.active_macro = self.active_macro
        return g

    def _micro_bits(self, m):
        return ((self.x | self.o) >> (m * 9)) & 0x1FF

    @staticmethod
    def _win_mask(mask):
        for a, b, c in LINES:
            line = (1 << a) | (1 << b) | (1 << c)
            if mask & line == line:
                return True
        return False

    def micro_winner(self, m):
        base = m * 9
        if self._win_mask((self.x >> base) & 0x1FF):
            return X
        if self._win_mask((self.o >> base) & 0x1FF):
            return O
        return None

    def macro_open(self, m):
        if (self.mx | self.mo) & (1 << m):
            return False
        return self._micro_bits(m) != 0x1FF

2.5 狀態編碼 encode()：深度學習側的接口

alphazero.py 的 encode()（第 88–111 行）把遊戲狀態轉為固定形狀輸入張量 [4, size, size]（size = 3 或 9）：

  • 通道 0：X 子位置（1.0）；通道 1：O 子位置（1.0）——兩者互斥。

2.6 重要修正：本專案沒有「合法動作掩碼（Action Masking）」

本專案的 MCTS 直接以 legal_moves() 枚舉合法走法建立子節點（mcts_search 第 327–343 行），而 Policy Head 輸出完整 81 維 logits。擴展時僅從 probs 中取出合法子集的先驗：

  • softmax 在全 81 維計算、不重新歸一化（第 317、334–339 行）——非法動作的機率質量既未在輸出端遮罩，也未在取子集後重新分配。
  • 優點：架構與合法集合完全解耦——不需要為每一局面維護動態遮罩張量；固定 81 維輸出使 batch 形狀恆定（配合 D17 的固定 256 寬批次，MIOpen 每個 kernel 只查一次）；搜尋端由 legal_moves() 保證零非法走法。
  • 缺點：機率質量會「洩漏」到非法動作，使合法子集的相對先驗被系統性壓縮（尤其當合法集合很小時，如殘局只剩數手）；先驗在合法子集上不具備標準 AZ 的歸一化語意。實務上因 UTTT 分支因子大、非法動作占多數但機率分散，此偏差可被搜尋修正，但這是「以程式碼現況」必須記錄的取捨。

3遊戲側演算法與優化遊戲側

3.1 Basic：吃子、擋棋與位置偏好

get_basic_move()（ai.py 第 105–145 行）是純規則對手，依序：

  1. 能贏就贏：逐一測試 apply_clone_result(game, m) == player（第 110–112 行）——下這手若立即勝利則回傳。
  2. 避免送勝：找出會讓對手下一手立即獲勝的「敗著」並排除（第 114–122 行）；若存在安全著法，隨機選擇其一。

3.2 Minimax：alpha-beta 剪枝與深度加權終局分

  • 節點數實測（空盤普通 3×3，本機量測）：無剪枝 549,946 → 有剪枝 20,866，節省 96.2%。
  • 走法排序是關鍵：先搜「最可能好」的走法，alpha 很快收斂到正確值，後續分支被剪得更多。minimax_move_normal() 以 sorted(..., key=lambda i: i != 4) 把中心放最前（第 167 行）。
  • 與 Minimax Pro 的關係：§3.4 的 _negamax_tt（第 1044–1099 行）是同一思想的工程化版本（negamax 形式 + 置換表 + Killer/LMR）——Killer 與 LMR 本質上都是「更好的走法排序 → 更多剪枝」。

4.3.1 Selection：PUCT 與 Q 的存儲視角

SearchNode.best_child()（第 211–224 行）的選擇公式為：

\[ \mathrm{PUCT}(s,a) = -Q(s,a) + C_{puct}\cdot P(s,a)\cdot \sqrt{\frac{\log\big(N(s)+N_v(s)\big)}{N(s,a)+N_v(s,a)}} \]

兩個關鍵設計（皆有程式碼依據）：

  • Q 的存儲視角：q 以「該節點狀態的行棋方」為視角儲存（第 191–192 行類別註解、第 281 行 n.q = n.wins / n.visits）。因此在父節點選擇時，子節點的 q 是「對手視角」，必須取負號才是對父節點行棋方的價值——這就是公式中 −Q(s,a) 的來源，與回饋端的 negamax 交替（第 282 行 value = -value）互為鏡像。
  • 虛擬損失：VIRTUAL_LOSS = 2.0（第 180 行）在批選過程中對路徑上每個節點加 v_visits += 1、v_wins += VIRTUAL_LOSS（第 297–299 行），使同一輪內並行的選擇器傾向走不同分支，並在回饋時移除（第 274–277 行）。注意虛擬損失加到 v_wins 是「正值」，會壓低 −q 項，刻意讓已被佔用的分支在虛擬期間失寵——這是發散作用而非統計修正。
與文獻公式的差異：經典 AlphaZero 的 PUCT 分母通常寫為 \(1+N(s,a)\)，本專案實作（第 212–221 行）為 \(\sqrt{\log(N_{\mathrm{parent}})/N_{\mathrm{child}}}\)，沒有 +1。由於本專案採全展開（見下），子節點必有 \(N\ge 1\)，+1 的保護作用被最小化；此處以實際程式碼為準，並於附錄 A 記錄此差異。

每個葉子首次被評估後立即全展開：為所有合法走法建立子節點並寫入先驗（第 325–344 行）。根節點在首次展開時以 dirichlet_alpha 加入探索噪聲：

\[ P'(s,a) = (1-\varepsilon)\,P(s,a) + \varepsilon\,\eta_a,\qquad \eta \sim \mathrm{Dirichlet}(\alpha),\quad \alpha = \frac{10}{|\mathcal{A}(s)|},\quad \varepsilon = 0.25 \]

4.4 同步批次整合（非異步）：葉子並行批推理

本專案的批推理是同步（synchronous）的：同一搜尋回合內收集多個葉子，一次前向，而非異步（asynchronous）樹並行。實作細節（第 306–318 行）：

  • 固定 256 寬填充批次：pad = batch_size - len(leaves)，以 leaves + [leaves[0]] * pad 填滿（第 312–313 行）。每個行程只出現一種張量形狀，MIOpen 只需查一次 kernel（決策 D17 的核心動機）。
  • 單次前向 + 兩次 CPU 拷貝：policies, values = model(states) 一次前向，接著 softmax 在 GPU 上完成後各以一次 .cpu().numpy() 同步拷回（第 317–318 行），並以 [:len(leaves)] 丟棄填充重複項。相較於逐葉子同步（每搜尋最多 160 次，見 6.3 節），這把同步次數壓到每輪固定次數。
  • 重複葉子偵測：queued = set() 以節點 id 記錄本輪已收集的葉子；若「尚未展開的節點」已在佇列中（node.untried and id(node) in queued，第 294–295 行），立即停止收集並先做一次前向——防止小預算全部浪費在對同一未展開根節點的重複選擇上。
  • 終局節點直接回傳：選擇到 node.untried == [] 的終局節點時不走網路，直接以 terminal_value 回饋（第 301–302 行）；terminal_value()（第 121–127 行）以「下一步行棋方視角」回傳 −1（敗）或 0（和），與網路價值慣例一致。

def _train_multiprocess(make_game_fn, model, optimizer, evaluate, replay, games,
                        sims, eval_every, lr, save, quiet, steps_per_game,
                        replay_cap, size, channels, blocks, ckpt_every,
                        dirichlet_eps, workers, game_type, start,
                        rollout_weight):
    """Multi-process self-play.

    A worker pool plays the games (each task carries the latest weights and
    uses its own GPU model copy); the main process collects results, runs the
    optimizer, checkpoints and evaluates. Spawn context is required on
    Windows; the pool transparently replaces crashed workers.
    """
    import multiprocessing as mp
    ctx = mp.get_context('spawn')
    results_q = ctx.Queue()
    pool = ctx.Pool(workers, initializer=_mp_worker_init, initargs=(results_q,))

    def submit(idx):
        weights = {k: v.cpu() for k, v in model.state_dict().items()}
        return pool.apply_async(
            _mp_play_game,
            (idx, weights, size, channels, blocks, sims,
             dirichlet_eps, games, game_type, rollout_weight))

    next_idx = 1
    for _ in range(min(workers * 2, games)):
        submit(next_idx)
        next_idx += 1

    done = 0
    while done < games:
        idx, data = results_q.get()
        done += 1
        if isinstance(data, Exception):

                  % (game_type, idx, data), flush=True)
        else:

            replay.append((states, targets, zs))
            if len(replay) > replay_cap:
                replay.pop(0)
            optimizer.param_groups[0]['lr'] = lr * max(0.2, 1.0 - done / games)
            model.train()
            total_loss = 0.0
            for _ in range(steps_per_game):
                g_states, g_targets, g_zs = random.choice(replay)

                loss_p = -(F.log_softmax(pred_p, dim=1) * target).sum(dim=1).mean()

                (loss_p + loss_v).backward()

def mcts_move_parallel(game, iterations, workers=4):
    """Run several independent MCTS searches and merge their root stats."""
    chunk = max(1, iterations // workers)
    results = []
    if cfg_engine('bitboard', True) and isinstance(game, UltimateGame):
        base = BitUltimateGame.from_game(game)
    else:
        base = game

    def work():
        results.append(mcts_search(base.clone(), chunk))

    threads = [threading.Thread(target=work) for _ in range(workers)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    stats = {}
    for root in results:
        for c in root.children:
            s = stats.setdefault(c.move, [0, 0.0])
            s[0] += c.visits
            s[1] += c.wins
    if not stats:
        moves = game.legal_moves()
        return random.choice(moves) if moves else None
    best_move = max(stats, key=lambda m: stats[m][1] / max(1, stats[m][0]))
    best_ratio = stats[best_move][1] / max(1, stats[best_move][0])
    for m, (v, w) in stats.items():
        if w / max(1, v) == best_ratio:
            g = game.clone()
            apply_move(g, m)
            if g.result() == game.current:
                best_move = m
                break
    return best_move

6.3 GPU 利用率診斷（優化歷程）

在 Windows 原生 ROCm（TheRock wheel，RX 7900 XTX / gfx1100，見 docs/rocm-wsl2.md）上，微型網路 + 串行 MCTS 的主要瓶頸並非算力而是kernel 啟動與同步開銷：

  • 每 conv kernel 啟動阻塞約 640 µs，佔自對弈時間約 60%——128 通道 × 5 塊的網路每次前向僅數 ms，但數十次 kernel 啟動逐次阻塞，浪費遠超計算本身。
  • 逐葉子同步 160 次/搜尋：改良前每個葉子一次同步往返；改為葉子並行批次後，每搜尋回合僅一次前向 + 兩次 CPU 拷貝（見 4.4），同步次數從 160 降到個位數。
  • 刪除選擇階段冗餘 clone、去 shuffle（SearchNode 第 204–206 行註解說明展開順序無關，故不需洗牌）、numpy 化先驗：把 Python/張量層的每迭代固定成本壓低。
  • 固定形狀批 + MIOpen 設定：alphazero.py 在 import 時設定 MIOPEN_USER_DB_PATH / MIOPEN_CUSTOM_CACHE_DIR / MIOPEN_FIND_MODE=1 / MIOPEN_FIND_ENFORCE=NONE（第 34–48 行），把 find-db 與 kernel cache 指到專案內磁碟並跳過不穩定的即時 benchmark；配合固定 256 寬批次，每行程只查一次 kernel。
  • 為何微型網路 + 串行 MCTS 無法打滿 GPU：單次前向計算量小（約 158 萬參數），而 MCTS 的選擇/rollout 是 CPU 工作且與前向串行；合理的優化目標是「對局吞吐」而非 GPU 利用率——8 worker 多進程自對弈把 GPU 前向與各 worker 的 CPU 搜尋重疊，6000 局牆鐘由 7.1 小時降到 62 分鐘（D18）。

6.4 診斷方法論：過擬合、策略崩塌與搜尋退化

  • 過擬合：Replay Buffer 只含近 100 局，理論上容易對近期自對弈過擬；但自對弈對手即當前模型，分布持續漂移，因此觀察重點是「評估勝率 vs 隨機」是否與 loss 同步改善。本專案觀察到評估勝率飽和而 loss 持續下降的分離——loss 反映的是對「近期自對弈分布」的擬合，勝率才是泛化指標。
  • 策略崩塌（Policy Collapse）：若 Dirichlet 噪聲太弱或 τ 退火太快，模型可能過早鎖定少數走法而喪失探索，自對弈分布退化為對稱盲點。本專案以 ε=0.25 根噪聲 + τ 1.0→0.05 慢退火對抗，且低溫選步以「價值最高」取代「最多訪問」（第 365–379 行），避免噪聲誘導的熱門誤導。
  • 搜尋退化：全展開 + 先驗引導在固定小預算下，若先驗質量不足，訪問會集中於少數高先驗分支而缺乏深層修正——「vs 隨機 95% 但 vs 啟發式 MCTS 2W/1D/3L」即為此現象的邊界證據；純網路（w=0）的平台期（70–76%）也顯示沒有 rollout 訊號時搜尋難以自我校正。

7結論與未來研究雙側

7.1 雙線總結

  • 遊戲側：傳統演算法與位板優化已達成熟——Minimax Pro 具備工業級搜尋元件（置換表/Killer/LMR/Aspiration/疊代加深），MCTS 家族具備動態 UCT、啟發式 rollout、樹重用與並行化；MCTS/RAVE/GRAVE 於現行優化下統計持平（D21 取代 D8/D12 舊排名）。
  • 深度學習側：AlphaZero 在 6000 局內學會壓制隨機（95%，38W/1D/1L），並證明「遊戲側啟發式」與「神經先驗」的混合（w=0.5）在資料效率上遠勝純網路；同時以 2W/1D/3L 對啟發式 MCTS 的結果誠實標出當前邊界。
  • 工程面：Windows ROCm 環境的 kernel 啟動問題（640 µs/次）被固定形狀批次、批次化推論與多進程自對弈有效消化；單檔模組化（D2）使兩側優化可獨立演進、互相復用。

7.2 未來研究方向

  • MuZero / LightZero 機制：以潛在模型取代顯式狀態編碼，免除人工 4 通道特徵設計，並讓網路自己學習「遞移規則」的轉移函數。
  • 位板 + 原生算子壓縮 MCTS 常數：把 BitUltimateGame 的整數運算向量化（batch bit ops），或移入 C/C++ 擴充，壓縮樹搜尋的每迭代常數。
  • 模型量化 / 剪枝：158 萬參數的微型網路在 CPU 推理上仍有量化空間，可降低自對弈與部署延遲。
  • 更強評估基準：與 Minimax Pro、GRAVE 的正式對戰矩陣（多 sims、多深度、先手平衡），取代「vs 隨機」作為主要指標。
  • 斷點續訓與 worker 容錯重派：目前 worker 失敗僅記錄（第 601–603 行），可加入任務重派與檢查點續訓。
  • 殘局表輔助 AZ 葉子評估：在微觀殘局（空格 ≤ 2）以 build_micro_tablebase() 精確值取代 rollout/網路估值，提升終局精度。
